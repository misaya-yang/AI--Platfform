# Hejaz AI Gateway — Design Context

> The persistent design brief for the AI Gateway web console.
> All frontend work (components, pages, illustrations, motion, copy) should
> route through this document. Update it when direction shifts — don't drift.

---

## Design Context

### Users

**Internal only.** The console is used by Hejaz's own engineers, operators,
and a small admin cohort who:

- **Monitor** — watch latency, cost, token usage, provider health across services
- **Govern** — manage users, rate limits, API keys, security events
- **Configure** — wire providers, models, knowledge bases, MCP integrations
- **Debug** — follow traces, inspect sessions, trigger test runs, read logs

They open this thing for hours a day. It's their control room, not a landing
page. Information density matters; cognitive load matters; emotional tone
matters (staring at ugly all day is a cost).

**Not serving:** end customers, executives, marketing audiences. The
Islamic-content product layer is a separate surface — the Gateway is
infrastructure and should feel like infrastructure, not like a religious
experience.

### Brand Personality

Three words: **Sharp. Modern. Confident.**

The Gateway is the "instrument panel" behind Hejaz's AI products. It should
feel like a precision tool — built by people who care about typography and
motion — not a generic "enterprise admin dashboard."

**Explicit emotional goals:**
- **Composure over urgency**: metrics that are "fine" should feel calm, not
  scream green checkmarks. Only real problems should visually interrupt.
- **Editorial confidence**: typography with opinions. Headlines have
  presence. Labels know their place. No shouty uppercase everywhere.
- **Craft signals**: small details (hairlines, letter-spacing, an easing
  curve) tell the user someone cared. This is the differentiator.

### Aesthetic Direction

**North star reference:** the `OPENCLAW Gateway Dashboard` screenshot the
user shared. This is a **direct aesthetic adoption**, not "inspired by" —
the user explicitly said "人家弄的很干净" (theirs is clean), take the
typography, the layout, the palette. Don't over-invent a separate identity.

**What to literally copy from the reference:**
- Near-white warm canvas, single signature red as the only accent
- Tight editorial sans-serif with the lockup pattern: big bold wordmark
  stacked over a small all-caps subtitle (like `OPENCLAW` / `GATEWAY
  DASHBOARD`)
- A small animal mascot in the top-left corner next to the wordmark
- Pill-shaped status chips with a tiny colored dot (`● 健康状况 正常`)
- Round icon buttons with the red accent as background tint for active ones
- Generous whitespace; hairlines instead of card borders
- Left-aligned page title (`聊天`) with small muted subtitle beneath
- Chat layout with full-width message rows, no heavy bubbles — just
  indentation + small avatar + timestamp

**Direction in one sentence:** *Take OPENCLAW's playbook and apply it to
every page of the Gateway — clean light canvas, red as the whole voice,
editorial type, small animal mascot.*

**Palette**

- **Canvas / ink**: warm-tinted neutrals. Pure #fff and #000 banned. Lean
  toward a whisper of red in the warm grays (e.g. `oklch(0.98 0.005 25)` for
  surface, `oklch(0.20 0.015 25)` for ink) so the whole UI subconsciously
  matches the signature color.
- **Signature red**: a *vermilion / signal-red* — NOT pure `#FF0000` and NOT
  generic SaaS crimson. Starting target: `oklch(0.60 0.22 27)` ≈ a warm,
  slightly rusty red with body (think vermillion pigment, signal-flare, lobster
  shell). This is the ONLY accent. It carries:
  - primary CTAs
  - active navigation
  - live-data indicators (pulsing dot)
  - destructive state (at higher saturation)
  - brand marks
- **Semantic greens / ambers for status**: used sparingly — small dots, not
  full badges. Never compete with the red.
- **Nothing neon, nothing purple, nothing cyan, no gradient text.**

**Typography**

- **Display (headlines, KPIs, brand)**: a sharp editorial sans with
  personality — candidates: *Söhne*, *Fraunces display*, *ABC Diatype*, or
  keep *Geist* but restricted to `font-weight: 500/700` with tight
  `letter-spacing` and much larger sizes. Final pick in implementation.
- **Body**: Geist Sans stays — it's clean and international.
- **Mono (numbers, code, task IDs)**: IBM Plex Mono stays — signals
  "this is data."
- **Arabic**: Noto Naskh Arabic — unchanged, RTL must never break.
- **Chinese**: Noto Sans SC chain — unchanged.
- **Scale**: modular, fluid (`clamp`). Big headlines (40–56px on desktop).
  Tight small caps for section eyebrows (`text-xs uppercase tracking-wider`).
  No more than 3 active type sizes on a given screen.

**Layout**

- **Kill the card grid.** Not everything needs a rounded rectangle. Use
  horizontal hairlines (`border-b border-ink/8`), vertical whitespace,
  and asymmetric column splits for hierarchy.
- **Asymmetric by default.** Wide left content + narrow right rail is
  better than "3 equal columns."
- **Rhythmic spacing.** Tight groupings (4px/8px) inside a unit, generous
  (48–80px) between units. Monotone 24px padding everywhere is the anti-goal.
- **Container queries** (@container) for component-level responsiveness —
  don't rely purely on viewport breakpoints.

**Decoration**

- **A mascot.** Same treatment as OPENCLAW's lobster: small, cute, placed
  beside the wordmark in the top-left. Not Hejaz-owned-and-unique; just
  a different cute animal rendered in the same flat illustrated style.
  Candidate picks to try in implementation (ordered by my preference):
  **(1) fennec fox** (desert ears, cheeky, matches AI assistant vibe),
  **(2) falcon chick** (regional symbolism, compact), **(3) oryx** (clean
  silhouette, one horn forward), **(4) camel calf**. Pick one during
  implementation and commit. Emoji-adjacent but rendered as a proper flat
  illustration, not a stock emoji.
- **Intentional negative space** around it. The mascot is punctuation, not
  wallpaper.
- **Hairline rules** (0.5px–1px) over drop shadows. Shadows only for
  floating elements (popovers, modals).
- **No glassmorphism. No neon glows. No sparkline soup. No icon-in-rounded-
  square-above-every-heading.**

**Motion**

- **Exponential easing only** (`cubic-bezier(0.16, 1, 0.3, 1)` and similar).
  Never bounce. Never elastic.
- **One orchestrated page-load sequence** per route (staggered entrance,
  ≤400ms total) > a dozen scattered hover wiggles.
- **Transform + opacity only** for performant transitions.
- **Respect `prefers-reduced-motion`** without discussion — hard requirement.

**Theme**

- **Follow system** is the default. Light mode is the "home" aesthetic —
  design decisions start there. Dark mode is the inversion, not a separate
  aesthetic universe. Both must feel like the same product.
- **Manual override** toggle available (sun/moon/auto tri-state) in
  top-right.
- **Warm-tinted dark mode**: ink inverts, red accent warms up slightly to
  keep contrast on dark surfaces.

### Design Principles

These are the filters for every implementation decision. If a design choice
doesn't pass these, redo it.

1. **One accent, used with discipline.** The signature red is load-bearing.
   If a page needs a second color to make sense, the information
   architecture is wrong — fix the structure, don't add a color.

2. **Editorial over enterprise.** Treat every screen like a page in a
   well-designed magazine — headline, dek, body, margin, footer. "Dashboard"
   doesn't mean "dump 12 cards in a grid."

3. **Composure at rest, drama on change.** The UI should be quiet when
   nothing is happening. Change (a new event, a tool call finishing, a
   cost spike) earns motion and color — earns attention.

4. **Density with breathing room.** Operators need information. But
   density ≠ tightness. Achieve high information per screen through
   *hierarchy*, not through shrinking everything.

5. **Craft is the differentiator.** A focus ring that's 2px wider than
   default, a letter-spacing choice, an easing curve. Users can't
   articulate these, but they feel the difference. Sweat this.

6. **Every icon earns its place.** If it duplicates the label, it's
   clutter. Use icons for action affordance, status, or brand — not
   decoration.

7. **Speed is design.** Instant feedback, optimistic UI, skeleton
   loaders that match the final layout (not generic gray blocks).

8. **i18n + RTL are first-class.** Nothing breaks when the user
   switches to Arabic. Test RTL on every new component.

### Technical constraints

- **Stack locked in:** React 18 + Vite + Tailwind 3 + Radix UI primitives +
  framer-motion + recharts + react-i18next.
- **AntD is on the chopping block.** For the redesign, prefer Radix + custom
  components. Keep AntD temporarily only where replacement cost is very high
  (e.g. `DatePicker`); style it aggressively via overrides until it can be
  replaced.
- **Accessibility target: WCAG AA** for all new components. Focus rings,
  keyboard navigation, aria labels, reduced motion — not optional.
- **Performance budget:** first paint < 1.5s on mid-tier laptop,
  interactions < 100ms.

### Anti-references (explicit "don't look like this")

- The current state (dark green + gold, flat card grid, weak hierarchy) —
  the thing we're replacing.
- Generic Shadcn landing pages (template soup).
- Anthropic console (too corporate-beige for our energy).
- Any "dark mode with cyan/purple neon" AI dashboard from 2024.
- Generic enterprise admin UIs (SAP, Salesforce, anything "Lightning").

### What is NOT an anti-pattern (explicit permission)

- **Copying OPENCLAW's aesthetic directly is the goal.** If our chat page
  looks like their chat page at a glance, that's success. The reference
  was chosen because it works — we're not trying to beat them on
  originality, we're trying to match their cleanliness on Hejaz content.

## Working rules for this project

- New UI work happens on `0417` branch (user's convention for this redesign).
- Frontend changes stay local (dev server only) until explicitly promoted —
  backend deploys independently on different windows.
- Use Playwright MCP for visual regression and interaction testing during
  iteration.
- Review against this document before shipping any page. If the work
  violates a principle, the document wins — either the work changes or
  this document changes, but they don't coexist in conflict.
